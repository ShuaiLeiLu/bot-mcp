## 二、完整调度时序

### 1. 调度扫描

1. 调度器每 **15 秒**扫描一次到期任务。
2. 普通渠道距离上次探测完成满 **60 秒**后进入任务队列。
3. “60 秒一次”是到期条件，不是固定时刻任务；通常在上次探测完成后的 **60～75 秒**开始。
4. 上一轮耗时、并发上限和排队会继续推迟开始时间。
5. 人工排除的渠道不探测。
6. 分组级探测设置优先于全局设置。

### 2. 样本获取

Guardian 同时接收两类样本：

- **主动探测**：调用 Sub2API 账号测试接口，记录首字延迟与结果。
- **真实流量**：从 Sub2API ops 请求日志拉取真实请求结果。

当前采样参数：

| 参数 | 当前值 | UI 范围/步进 | 说明 |
|---|---:|---|---|
| 主动探测 | 开启 | 开关 | 只控制未熔断渠道的常规巡检。 |
| 探测间隔 | 60 秒 | 最小 30，步进 1 | 到期条件。 |
| 探测超时 | 60 秒 | 最小 5，步进 1 | SSE 测试最长等待时间。 |
| 探测并发 | 4 | 1～32 | 同时测试的渠道数。 |
| 全局测活模型 | 空 | 文本 | 空值使用账号默认模型。 |
| 测活提示词 | `hi` | 文本 | 测活请求提示词。 |
| 接入真实流量 | 开启 | 开关 | 要求 Sub2API 开启 ops。 |
| 流量拉取间隔 | 60 秒 | 最小 10 | 拉取真实请求样本。 |
| 流量回溯窗口 | 120 分钟 | 最小 5 | 每次拉取的历史窗口。 |
| 每渠道最多取样 | 60 条 | 5～200 | 控制真实样本规模。 |
| 真实样本新鲜期 | 180 秒 | 最小 10 | 判断真实样本是否足够新鲜。 |
| 新鲜流量时跳过探测 | 关闭 | 开关 | 当前即使存在新鲜真实流量，仍继续主动探测。 |

熔断渠道的恢复探测不受“启用主动探测”控制；它由“健康回池”单独控制。否则熔断渠道没有真实流量，永远无法自动复活。

## 三、健康分公式

### 1. 事件分值

| 样本类型 | 当前分值 | 可配范围 |
|---|---:|---:|
| 完美健康 | 100 | 0～100 |
| 首字慢 | 65 | 0～100 |
| 上游未知异常 | 40 | 0～100 |
| 网关错误（5xx） | 25 | 0～100 |
| 限流 / 额度耗尽 | 15 | 1～100 |
| 探测失败 | 10 | 0～100 |
| 凭据失效 / 致命错误 | 0 | 0～100 |

评分阶段的“首字慢”阈值为 **5000ms**。注意它与熔断规则中的 **15000ms** 慢响应阈值不是同一个参数：

- 超过 5 秒：该样本按 65 分计入健康分。
- 熔断延迟窗口使用 15 秒阈值，但当前“延迟超标只降级不熔断”已开启。

### 2. 短期分与长期分

- 短期窗口：最近 **10** 条样本。
- 长期窗口：最近 **60** 条样本。
- 短期分占最终分：**0.7**。
- 长期分占最终分：**0.3**。
- 短期窗口中最新一条样本权重：**0.5**。
- 其余短期样本按公比 **0.5** 几何衰减，归一化后共同占剩余 50%。
- 长期分是长期窗口均值。

公式：

```text
短期分 = 最新样本 × 0.5
       + Σ(其余样本_i × 0.5^i / Σ0.5^i) × 0.5

最终健康分 = 短期分 × 0.7 + 长期分 × 0.3
```

公比 0.5 已使用页面实时样本反算验证：样本分值
`[65,40,65,10,100,15,100,15,15,100]` 得到短期分
`55.62133072407043`，与页面 API 返回值完全一致。

以下 HTTP 状态始终视为致命凭据类错误：




## 四、熔断、降级与保底

### 1. 错误率熔断

| 参数 | 当前值 | UI 范围 |
|---|---:|---|
| 熔断开关 | 开启 | 开关 |
| 错误率窗口 | 5 次请求 | 最小 1 |
| 窗口内失败次数 | 3 次 | 最小 1 |
| 同时要求健康分低于 | 60 | 0～100 |
| 每轮最多熔断 | 1 个 | 最小 1 |
| 熔断冷却 | 180 秒 | 最小 0 |
| 见到即熔断状态码 | 空 | 逗号分隔 |
| 凭据失效立即熔断 | 开启 | 开关 |

普通软熔断要求同时满足错误窗口和健康分条件。每轮最多熔断 1 个，用于防止多个渠道同时被摘除造成雪崩。

### 2. 网关错误、限流和延迟

- **短时 5xx**：当前只降级、不立即熔断。
- **整个错误窗口持续失败**：仍可进入临时熔断，恢复后自动回池。
- **带 `rate_limit_reset_at` 的临时限流**：不摘除，只降低权重；窗口重置后恢复。
- **持续余额/额度不足**：达到错误门槛后可熔断。
- **延迟超标**：当前只降级、不熔断。

### 3. 延迟窗口

| 参数 | 当前值 | UI 范围 |
|---|---:|---|
| 延迟窗口 | 10 次请求 | 最小 1 |
| 慢响应次数 | 5 次 | 最小 1 |
| 慢响应首字界限 | 15000ms | 最小 100ms |
| 延迟超标只降级 | 开启 | 开关 |

### 4. 保底池

| 参数 | 当前值 | UI 范围 |
|---|---:|---|
| 保底可用渠道数 | 1 | 最小 0 |
| 计入可用池最低分 | 3 | 0～100 |

当一次熔断会使分组可用渠道低于保底数时，不执行普通熔断，而进入“保底强留”并告警。保底规则同样约束致命错误快速熔断，防止把整个分组打空。

### 5. 降级

| 参数 | 当前值 | UI 范围 |
|---|---:|---|
| 启用降级 | 开启 | 开关 |
| 降级线 | 75 | 0～100 |
| 优先级步进 | 1 | 1～4 |
| 负载乘数 | 0.5 | 0.05～1，步进 0.05 |
| 最低负载因子 | 1 | 最小 1 |

低于降级线的渠道仍在池内，但优先级变差、负载因子降低。慢渠道优先降权而不是直接摘除。

## 五、健康回池

| 参数 | 当前值 | UI 范围 |
|---|---:|---|
| 健康回池 | 开启 | 开关 |
| 恢复探测间隔 | 180 秒 | 最小 30 秒 |
| 回池目标分 | 75 | 0～100 |
| 连续成功次数 | 3 | 最小 1 |
| 健康持续时间 | 60 秒 | 最小 0 |

熔断渠道每 3 分钟进行一次低频恢复探测。达到至少 75 分、连续成功 3 次，并持续健康 60 秒后：

1. 恢复调度；
2. 还原正常优先级和负载因子；
3. 重新进入可用池。

关闭健康回池后，熔断渠道只能人工恢复。

## 六、价格、速度、权重和写回

### 1. 当前全局策略

```text
strategy = price（价格优先）
```

可选模式：

- **价格优先**：低有效价格渠道获得更多调度份额。
- **速度优先**：低首字延迟渠道获得更多调度份额。
- **均衡**：在价格与速度之间按比例混合。

### 2. 权重参数

| 参数 | 当前值 | UI 范围 |
|---|---:|---|
| 每组权重预算 | 400 | 最小 1 |
| 权重健康闸门 | 40 | 0～100 |
| 均衡中价格占比 | 0.5 | 0～1，步进 0.05 |
| 价格权重强度 | 1 | 最小 0.1，步进 0.1 |
| 速度权重强度 | 1 | 最小 0.1，步进 0.1 |
| 微调防抖阈值 | 0.1 | 0.01～1 |
| 调整冷却 | 60 秒 | 最小 0 |
| 负载因子下限 | 1 | 最小 1 |
| 负载因子上限 | 100 | 最小 1 |

健康分低于 40 时权重归零。权重变化不足 10% 不写回；成功写回后进入 60 秒冷却，避免来回抖动。

**推断项：**字段 `price_exp`、`speed_exp` 和预算语义表明，系统会把价格/速度指标经指数强度换算后，在分组预算内归一化分配权重。页面没有公开精确归一化公式，因此不能断言具体除法、平滑或截断细节。

### 3. 写回范围

当前自动写回全部开启：

| 写回项 | 当前状态 | 含义 |
|---|---|---|
| `schedulable` | 开启 | 熔断与恢复上下池。 |
| `priority` | 开启 | 1～5，数值越小越优先。 |
| `load_factor` | 开启 | 承载流量比例。 |

关闭任一写回项后，Guardian 仍计算期望值，但不修改 Sub2API，适合观察模式。

## 七、分组级覆盖

每个分组可覆盖全局配置：

| 分组字段 | 默认来源 | 约束/说明 |
|---|---|---|
| 是否参与守护 | 全局守护范围 | 关闭后不探测、不熔断、不调权。 |
| 策略 | 全局 `price/speed/balanced` | 可单独选择。 |
| 保底可用渠道数 | 全局 1 | 最小 0。 |
| 权重预算 | 全局 400 | 最小 1。 |
| 均衡价格占比 | 全局 0.5 | 0～1，步进 0.05。 |
| 熔断 | 全局开启 | 分组开关。 |
| 健康回池 | 全局开启 | 分组开关。 |
| 负载因子调权 | 全局开启 | 分组开关。 |
| 定时测试 | 全局开启 | 关闭后只依赖真实流量。 |
| 测试间隔 | 全局 60 秒 | 最小 30，步进 30 秒。 |
| 测试模型 | 全局/账号默认 | 空值回落全局。 |

当前 5 个受管分组均为 `price`，没有检测到分组级 override，实际继承全局策略。3 个分组被排除，不参与调度。

## 八、渠道级设置与人工操作

| 字段/动作 | 约束 | 写回位置 |
|---|---|---|
| 优先级 | 1～5，越小越优先 | Sub2API `priority` |
| 负载因子 | 最小 1 | Sub2API `load_factor` |
| 并发上限 | 最小 1 | Sub2API 并发配置 |
| 调度倍率 | 最小 0，步进 0.01；0 回落类型默认 | 仅 Guardian 内部 |
| 测活模型 | 空值用全局默认 | Guardian 探测配置 |
| 暂停调度 | 不接流量，但继续探测和计分；不会因分数恢复而自动上线 | 守护范围 |
| 排除渠道 | 不探测、不调度、不计分，并恢复接管前配置 | 守护范围 |
| 手动熔断 | 立即停止调度 | 调度状态 |
| 解除熔断 | 人工回池 | 调度状态 |
| 立即探测 | 单次探测，不改变自动开关 | 样本库 |

若设置的探测模型被 Sub2API 模型映射重写，Guardian 不会绕过该映射；必须在 Sub2API 后台修改账号模型映射。

### 火箭（临时优先）

- 常用时长：10 分钟、30 分钟、1 小时、3 小时。
- 自定义：1～10080 分钟（最长 7 天）。
- 启动后：优先级设为 1，`load_factor` 在原值上增加 1000。
- 到期后：自动恢复原优先级和原 `load_factor`。
- 可续期，也可提前取消。
- 账号级配置会影响它所属的全部分组。

## 九、守护范围优先级

当前模式：

```text
managed_group_mode = all
```

过滤优先级：

1. **排除分组**：最高优先级，整组不探测、不熔断、不调权，现有配置保持不动。
2. **排除渠道**：完全不参与，恢复接管前配置。
3. **暂停渠道**：不接流量但继续探测计分，必须人工恢复。
4. **参与守护分组选择**：`all` 或指定分组。
5. **账号类型、平台过滤**：空值表示不限。
6. **分组自身启用开关**。

当前实例快照：

- 排除分组：`43, 44, 28`
- 暂停渠道：`1044`
- 排除渠道：`723`
- 账号类型过滤：空（全部）
- 平台过滤：空（全部）

“恢复全部渠道原始配置”会把 Guardian 改动过的优先级、负载因子、并发和调度状态恢复为接管前值。

## 十、探测费用口径

费用是估算值，不是上游账单：

```text
估算成本 = 模型输入/输出单价 × 估算 token × 账号倍率
```

- 定价来源：`/api/v1/admin/channels/model-pricing`
- 本地定价缓存：30 分钟
- 倍率优先：账号上游 billing 倍率 → 账号倍率 → 1.0
- 未知模型与图片探测：不猜价格，标为“未计价”
- 失败请求：按保守口径估算，可能已消耗输入 token
- 不统计：人工立即探测、普通用户流量
- 按账号主分组归属统计

## 十一、通知与审计

### Telegram 通知

- 状态/汇总群与异常群可分开配置。
- 未配置异常群时，异常、恢复和升级通知发送到状态群。
- 定时汇总使用北京时间（UTC+8），最多 5 个固定时间。
- 当前没有固定时间，界面说明仍按旧配置每 60 分钟汇总。
- 支持测试发送与立即发送。
- 退出 Web 登录不会停止后台调度。

### 事件审计

可观察到的事件包括：

- `apply`：渠道调度参数已更新。
- `probe_failed`：超时、429、503、模型不存在、并发超限等探测失败。
- 熔断、回池、保底与写回也属于页面设计的审计范围。

连接页说明每一次写回都有前后值记录，用于排查和追溯。

## 十二、规则执行顺序（可移植模型）

综合页面与 API，可以把该系统归纳为以下有序决策链：

```text
守护范围过滤
  → 拉取真实流量样本
  → 判断普通探测/恢复探测是否到期
  → 并发执行探测
  → 样本分类并赋分
  → 计算短期分、长期分、最终健康分
  → 应用致命错误/错误窗口/延迟窗口规则
  → 应用保底池约束与每轮熔断上限
  → 决定 healthy / degraded / fused / forced-keep
  → 按价格/速度/均衡策略分配权重
  → 计算 priority / load_factor / schedulable 期望值
  → 应用防抖阈值和写回冷却
  → 按自动写回开关更新 Sub2API
  → 写入事件审计与通知
```

## 十三、实现时必须保留的安全边界

如果把这套规则移植到现有 MCP 调度器，以下边界不能丢失：

1. 人工暂停与自动熔断必须是不同状态；人工暂停不能被健康回升自动恢复。
2. 排除状态必须恢复接管前配置，而不是简单设置为可调度。
3. 熔断前先检查分组保底池，禁止打空整个分组。
4. 恢复探测与普通主动探测分开控制。
5. 429/临时限流有恢复时间时只降权，不应立即永久关闭。
6. 短时网络/网关错误与凭据失效必须分类处理。
7. 所有自动写回必须有前后值和原因审计。
8. 写回需有变化阈值、冷却和每轮上限，防止震荡与雪崩。
9. 真实流量优先，主动探测兜底，但熔断渠道仍需独立恢复探测。
10. 精确后端权重归一化公式未由页面公开，移植前必须通过更多行为样本或服务端源码验证，不应凭字段名直接照猜。
