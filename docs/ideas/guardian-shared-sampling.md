# Guardian 共享采样与受控自动调度

## Problem Statement

如何让 Sub2API Guardian 在不重复发起高成本主动探测的前提下，利用现有渠道监控与真实流量形成可信、可解释的健康评分，并安全地自动调整渠道权重、优先级和可调度状态？

## Recommended Direction

采用“单一采集、多个消费者”的共享采样架构：现有 60 秒渠道监控是唯一常规采集者，持久化带版本号的渠道快照；Guardian 每 15 秒只扫描本地数据库，仅在发现未消费的新快照或新流量桶时重新评分。正常渠道不再由 Guardian 独立探测，系统熔断渠道可在预算内每 300 秒执行一次低频恢复探测，人工暂停、人工熔断和排除渠道永不自动探测或恢复。

评分从“最近 N 条样本等权”改为“固定时间桶 + 来源可靠度 + 时间衰减”，并把 `healthScore` 与 `confidence` 分开。没有新数据只降低置信度，不扣健康分；置信度不足时冻结自动写回。`load_factor` 承担连续权重分配，`priority` 只表达粗粒度健康层级，`schedulable` 只用于自动熔断与系统熔断后的回池，三类写回分阶段放权。

## Key Assumptions to Validate

- [ ] 现有渠道监控快照能稳定覆盖所有受管渠道；通过 24 小时缺失率与重复率报告验证。
- [ ] Sub2API ops 日志可以可靠归属到渠道且能排除监控自身请求；通过请求 ID、API Key/分组映射和 User-Agent 对拍验证。
- [ ] 每分钟时间桶足以反映故障而不会掩盖瞬时致命错误；通过历史回放和故障注入验证。
- [ ] `load_factor` 是主要流量权重控制量，`priority` 适合只做健康分层；通过观察模式输出与真实路由结果比较验证。
- [ ] 系统熔断渠道的 300 秒恢复探测能在可接受 Token 预算内恢复；通过探测台账和每日预算告警验证。

## MVP Scope

- 共享快照持久化、版本去重和一次性消费。
- `SHARED_MONITOR`、`TRAFFIC`、`RECOVERY_PROBE`、`MANUAL_PROBE` 四类来源。
- 60 秒时间桶、短/长半衰期评分、独立置信度和数据陈旧状态。
- 观察模式下完整计算状态、权重、优先级和可调度建议。
- 人工状态保护、分组保底、写回冷却和变化步长限制。
- 页面展示样本来源、快照年龄、健康分、置信度和建议动作。
- 首版只对一个非核心分组灰度 `load_factor` 写回。

## Not Doing (and Why)

- 不让正常渠道由 Guardian 独立主动探测——这正是本次要消除的重复成本。
- 不把 7 日可用率直接并入实时健康分——其时间尺度和分母不透明，容易重复计分。
- 不自动修改并发上限——并发与账号限额耦合，首版证据不足。
- 不自动恢复人工暂停、人工熔断或上游人工关闭——尊重人工控制权。
- 不在低置信度、数据陈旧或观察期未通过时写回——避免历史数据驱动错误动作。
- 不承诺复刻第三方未公开的精确权重公式——本系统明确使用可解释的自有 V2 公式。

## Open Questions

- 恢复探测每日全局上限最终采用“请求次数”还是“估算 Token/金额”作为硬预算。
- 单分组灰度观察期采用 24 小时还是覆盖一个完整业务高峰周期。
- 自动优先级写回是否在 `load_factor` 灰度稳定后默认开放，还是继续要求单独人工批准。
